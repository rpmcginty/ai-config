# Summary template

Section structure, a worked example, and length calibration for a generated codebase summary.
Read before writing any summary.
Adapt the sections to the repo; drop any that would be padding, but keep their order.

## Section structure

### 1. Opening (2-4 sentences, no heading)

What this is, what problem it solves, who calls it.
A reader must be able to stop after this and know whether the repo is relevant to their task.
Name the runtime and the distribution shape (library, CLI, service, batch job) because that governs everything downstream.

### 2. Commands

The commands that actually work in this repo, copied from CI config, Makefile, or the manifest's script section.
Never guess and never list a command you have not seen written down somewhere in the repo.
Cover: install/setup, test, lint/format, typecheck, build, run locally.
If a command has a non-obvious precondition (a running database, an env var, a login), say so on the same line.

### 3. Directory map

One line per top-level area, explaining why the area exists and what a contributor adds to it.
Skip directories the file tree already explains (`.github/`, `docs/`) unless something about them is surprising.

### 4. Key abstractions

The 3-7 types, modules, or concepts a session must know to make a change.
Each gets a name, a location, and a sentence on its role.
Prefer the load-bearing ones: whatever most other modules import, subclass, or pass around.

### 5. How the pieces fit

The main flow through the system, in prose or a short numbered list.
Trace one real path end to end (a request, a CLI invocation, a job run) with file names at each hop.
This is the section that saves the most time, because it is the one a file tree cannot convey.

### 6. Conventions

The output of the conventions audit (see `conventions-audit.md`), trimmed to the rules that change what a contributor writes.
Anchor each to evidence: the config that enforces it or the files that demonstrate it.

### 7. Gotchas and gaps

Deprecated modules, half-finished migrations, competing patterns, known-confusing areas, and conventions that are declared but unenforced.
Say plainly which side of a split pattern new code should follow.
A summary that hides warts costs more time than one that omits a whole subsystem.

### 8. Metadata block

The closing fence described in `SKILL.md`, matching the opening fence above the summary.

## Worked example

```markdown
# CLAUDE.md

<!-- codebase-summarizer: begin -->

`datalake-tools` is a Python library that wraps the team's S3 and Athena access so
analysis scripts do not each reinvent credential handling and partition discovery.
It is imported by the notebooks in `research/` and by the nightly jobs in
`airflow-dags`; it is not a service and has no network entry point of its own.

## Commands

    uv sync --all-extras          # install; requires Python 3.11+
    uv run pytest                 # full suite, ~40s
    uv run pytest -m "not aws"    # skip tests that hit real AWS (CI default)
    uv run ruff check . && uv run ruff format --check .
    uv run mypy src/              # strict mode, must stay clean

Integration tests need `AWS_PROFILE=datalake-dev` exported; without it they are skipped, not failed.

## Layout

- `src/datalake_tools/clients/` - one module per AWS service wrapper. Add new service clients here.
- `src/datalake_tools/schema/` - Pydantic models mirroring the Glue catalog. Regenerated by `scripts/pull_schema.py`, so hand edits are lost.
- `src/datalake_tools/query/` - Athena query builder and result paging. The largest area and the one most changes touch.
- `tests/fixtures/` - recorded AWS responses used by the offline tests. Record new ones with `scripts/record.py`.

## Key abstractions

- `Session` (`clients/session.py`) - the single credential entry point. Every client takes one; nothing constructs boto3 clients directly.
- `Table` (`schema/table.py`) - a catalog table plus its partition keys. Query building is typed against this, not against raw strings.
- `QueryPlan` (`query/plan.py`) - an unexecuted query. Built by `query.build()`, run by `Session.execute()`. Splitting build from execute is what makes queries testable offline.
- `ResultPage` (`query/results.py`) - lazy iterator over Athena output. Holds an open S3 handle, so it must be consumed inside its context manager.

## How a query runs

1. Caller gets a `Session` from `session.from_profile()`.
2. `query.build(table, filters)` returns a `QueryPlan`; no I/O has happened yet.
3. `Session.execute(plan)` submits to Athena and polls (`query/poll.py`, 2s interval, 15min cap).
4. Results stream back as `ResultPage` objects reading the S3 output location directly.
5. The caller's context manager exit deletes the S3 output prefix unless `keep_output=True`.

## Conventions

- All public functions carry full type annotations; `mypy --strict` gates CI (`.github/workflows/ci.yml`).
- Errors subclass `DatalakeError` (`errors.py`); raw `boto3` exceptions are wrapped at the client boundary, never propagated.
- Logging uses the module-level `logger = logging.getLogger(__name__)` pattern; no `print`, no root-logger configuration inside the library.
- Tests are function-based pytest with fixtures in `conftest.py`; no unittest classes anywhere in `tests/`.

## Gotchas

- `clients/redshift.py` is deprecated (docstring says so, nothing imports it) and is scheduled for deletion. Do not extend it.
- Two config styles coexist: `config.py` reads env vars directly, while newer code takes a `Settings` object. `Settings` is the intended direction; the env-var reads predate it.
- `schema/` is generated but committed, so a stale `schema/` and a live Glue catalog can disagree. Re-run `scripts/pull_schema.py` before trusting a column list.

<!-- codebase-summarizer: end; generated 2026-07-30, commit a1b2c3d, 24 claims -->
```

Note what the example does not do: it never restates the directory tree without adding a reason, and every wart is stated with its consequence for the reader.

## Length calibration

- Small package, one concern: 60-120 lines.
- Medium repo, several subsystems: 120-250 lines.
- Anything pushing past ~300 lines: split it, per the placement table in `SKILL.md`.

Length follows the number of hard claims available, not the size of the repo, so a large repo with a simple shape gets a short summary.
When a section has nothing checkable to say, delete the section rather than filling it.
